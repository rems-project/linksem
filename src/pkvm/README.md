# linksem/src/pkvm

Lem models of what the Linux kernel does to the pKVM hypervisor object
(`arch/arm64/kvm/hyp/nvhe/kvm_nvhe.o`) between linking it into `vmlinux`
and the hypervisor running on its own page tables, expressed symbolically
over the values chosen at boot (section addresses, the hyp VA layout, the
detected CPU capabilities, the host's inputs) so that the resolved sections
can be compared byte for byte with the running machine once those values
are known (readdwarf-private-3 `test-objcheck-pkvm`, notes022, notes023).

- `pkvm_relocations.lem`: the hyp VA layout parameters and `kern_hyp_va()`
  as a symbolic function; `kvm_apply_hyp_relocations()`, which rewrites
  every absolute pointer the object's `.hyp.reloc` section names from a
  kernel image VA to a hyp VA.
- `pkvm_alternatives.lem`: the arm64 "alternatives" (`.altinstructions`)
  as the kernel applies them to the hypervisor's code in its two boot
  passes: plain replacements with `patch_alternative()`'s re-targeting of
  branches and `adrp`, and the callback functions the hypervisor uses
  (`kvm_update_va_mask`, `kvm_patch_physvirt_offset`,
  `kvm_get_kimage_voffset`, `kvm_compute_final_ctr_el0`,
  `kvm_patch_vector_branch`, `spectre_bhb_patch_wa3`, `alt_cb_patch_nops`);
  the host's writes into the hypervisor's data before `__pkvm_init` as
  further parameters; and `resolve_pkvm`, composing the link-time
  relocation (`Symbolic_resolution`, `Abi_aarch64_instruction_fields`),
  the boot pass, the `.hyp.reloc` rewrite, the host writes and the
  system-wide pass.

They depend on `src/generated_arm64_cpucaps.lem` (the kernel's cpucaps,
generated by `etc_linux/gen-arm64-cpucaps-for-lem`) and
`src/abis/aarch64/abi_aarch64_encodings_for_pkvm_alternatives.lem` (the
instruction encodings the patching writes).

## The wider work these are part of

The following is the summary commit message of the series that added these
modules (linksem commits `bf6dfb4..02ba03d`, 2299 lines over eleven new
files), kept here so that it is readable from the tree.  It was done with
the private repository readdwarf-private-3, whose notes016, notes017,
notes022, notes023 and notes025 carry the detail and the evidence.

> The question they answer is: given a relocatable object file and a
> machine running the program it was linked into, is the object's
> contribution to that machine's memory exactly what the object and the
> choices made at link and boot time say it should be?  The approach is to
> resolve the object *symbolically*, leaving the dynamically chosen values
> as variables, and to substitute only at the end.
>
> Generic (`src/`):
>
> - `symbolic_resolution.lem`.  A `resolution_env` of section base
>   addresses, imported symbol values, GOT slot addresses (all
>   `elf64_addr`), named parameters (`elf64_xword`) and named flags.  A
>   `sym_expr` over those leaves with the bit operations and a conditional,
>   built by injection from `Elf_symbolic`'s expressions so that type and
>   its users are untouched.  A section becomes its bytes from the object
>   plus a sparse overlay of symbolic words and deferred relocation checks;
>   `resolve_object` applies every section's relocations through the ABI's
>   interpreter and a per-target field specification, and
>   `concretise_section` evaluates the overlay under an environment.
>   Renderer and parser for environments.
> - `report_format.lem`.  The line-oriented text format the instrumentation
>   scripts write and these types read: comments, `[section]` headers,
>   `key = value` lines and `|`-tables, with a byte-for-byte round trip.
> - `abis/aarch64/abi_aarch64_instruction_fields.lem`.  Where each AArch64
>   relocation target's value goes in the word, and the linker's ADRP+ADD to
>   NOP+ADR relaxation as a conditional on a flag and the displacement.
>
> Linux and pKVM (`src/pkvm/`, `src/generated_arm64_cpucaps.lem`,
> `abis/aarch64/abi_aarch64_encodings_for_pkvm_alternatives.lem`,
> `etc_linux/gen-arm64-cpucaps-for-lem/`): the kernel's boot-time patching
> of the hypervisor object, symbolically: the two alternatives passes with
> their callbacks and the plain replacements with `patch_alternative`'s
> re-targeting, the `.hyp.reloc` rewrite of kernel VAs to hyp VAs, and the
> host's writes into hyp data as parameters.  The cpucaps come from the
> kernel's own list through a generator; the instruction encodings are
> written from the Arm ARM and were cross-checked against the Sail model of
> the architecture, which found one wrong mask.
>
> Checked: a small userspace object matches its linked executable and the
> memory of the process running under qemu-user; `kvm_nvhe.o` matches
> `vmlinux` over all 5,371 relocation sites of its allocated sections; and,
> resolved as the booted hypervisor, it matches the memory of the running
> machine, both the code and read-only sections at the end of
> `__pkvm_init_finalise` and the data sections before the hypervisor's own
> initialisation.  Perturbing a section base or flipping a cpucap is
> detected.

## Which Linux

These models follow the kernel in `rigorous-engineering/re-linux`, branch
`android17-6.18` (`Makefile`: 6.18.32 at commit `af7273337830`, September
2026).  That is the Android common kernel based on upstream Linux 6.18;
the pKVM implementation in `arch/arm64/kvm/hyp/nvhe` (host stage 2,
`pkvm_moveable_regs`, the fine-grained-trap mask tables, the `.hyp.reloc`
mechanism, the callbacks above) is the Android one, which is ahead of
upstream.  The generic alternatives machinery (`arch/arm64/kernel/
alternative.c`, `kvm/va_layout.c`, `kernel/proton-pack.c`) is upstream
6.18's.  Anything in these files that names a kernel function or a data
layout is to be re-checked against a different kernel: the entry format
of `.altinstructions`, the set of callbacks and what they read, the
`.hyp.reloc` format from `gen-hyprel.c`, and the list of cpucaps (which
is regenerated, not hand-maintained).
